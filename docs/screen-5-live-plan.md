# 第五屏"直播活动"与真实访客数据规划

状态：仅规划，尚未实现。写于 2026-11-12。

相关文档：[第三屏、第四屏与全局交互构思](screens-3-4-plan.md)。

## 已确定的决定

1. 在线人数、点赞飘心和简化统计**单独成一屏**，不拆散进现有主题。
2. 数据最终来自这个展示页的**真实访客**。
3. **只记录当前数据，不存历史**：没有数据库，所有人离开后数字归零。
4. 分两期做：**第一期用模拟数据，第二期接真实数据**。第一期就把数据来源封装成独立的一层，第二期只换这一层，格子不改。

## 为什么单独成屏

- 在线、反应、实时统计是同一类组件，成套出现才有意义；放进 AI 助手或团队工作台会显得牵强，也会破坏已完成的排版。
- 现有四屏都没有覆盖"实时与在场感"和"媒体内容"两类，这一屏一次补上。

## 第五屏：直播活动（建议 20 个）

主题是一场线上发布会的直播间。统计数字要"长在控件上"，不单独摆一排数字卡。

### 在场（4）

- 在线人数：头像叠放加滚动数字，有人进出时头像弹入弹出
- "正在观看"脉冲点加人数胶囊
- 加入提示：有人进入时短暂出现一行"某某加入了"
- 正在输入指示：三个跳动的点加人名

### 反应（4）

- 点赞按钮：点击后红心向上飘散，旁边的总数滚动增加
- 表情反应条：几个常用 emoji，每个带各自的计数
- 连击计数：短时间内连续点击时显示"×5"并放大
- 反应汇总胶囊：本场各类反应的占比

### 内容（5）

- 视频播放器控制条：播放、进度、时间、全屏
- 直播状态徽标：直播中、即将开始、已结束
- 字幕条：逐句切换
- 章节进度：分段的进度条，当前章节高亮
- 音量与画质菜单

### 互动（4）

- 实时投票：选项的票数条随投票增长
- 滚动评论：新评论从底部进入
- 问答置顶：被顶得最多的问题排到最前
- 举手排队：排队序号和"轮到你了"状态

### 统计（3）

- 在线人数迷你走势线：最近几分钟的变化
- 本场峰值与已进行时长
- 互动率环：有过反应的访客占在线人数的比例

### 亮点格子

- **点赞飘心**：演示时自动飘；访客自己点也会飘，数字同步滚动。接入真实数据后，别的访客点赞也会在你的屏幕上飘出来。
- **在线人数**：头像随真实进出而增减。

### 飘动 emoji 的实现约束

- 同时在屏的飘动元素设上限（建议 24 个），超出时丢弃最早的，避免有人连点时卡顿。
- 只做位移、缩放和透明度动画，不触发重排。
- 开启"减少动态效果"的访客不飘，只让数字变化。
- 飘动元素对读屏软件隐藏，计数变化用礼貌的实时播报。

## 第三屏里的轻量融入

电商里本来就有这类用法，所以在"商店与结账"里放两处，其余几屏不动：

- 商品图角落的"23 人正在看"。
- 收藏心形按钮旁显示收藏数。

这两处也读同一个数据层，第二期会一起变成真实数据。

## 数据层

所有格子只通过一个数据层取数，不直接接触数据来源。计划放在 `src/lib/live.ts`。

数据层对外提供的内容：

| 内容 | 说明 |
| --- | --- |
| 在线人数 | 当前数字，以及最近几分钟的取样（供走势线用） |
| 本场峰值 | 本次有人在线期间的最高人数 |
| 反应流 | 每一次反应事件：哪个 emoji、是不是自己发的 |
| 反应计数 | 本场各 emoji 的累计数 |
| 发送反应 | 格子调用它来点赞 |
| 状态 | `simulated`（模拟）、`live`（真实）、`offline`（真实但连不上，已退回模拟） |

用法和现有的 `useSetting` 一致：一个外部 store 加一个 hook，格子订阅自己需要的那一项。

## 第一期：模拟数据

目标是把第五屏完整做出来，观感和接入真实数据后一致。

- 数据层的实现是一个模拟器：在线人数在一个区间内缓慢起伏，反应按随机间隔产生，偶尔来一小波连续点赞。
- 模拟器接受现有的全局演示控制：暂停时停、速度控件对它生效、离开屏幕时停。
- 访客自己的点击立即生效（飘心、计数加一），和模拟产生的反应走同一条通道。
- 这一期不引入任何外部服务，页面仍是纯静态。

完成标准：

- 第五屏 20 个格子全部可交互，通过类型检查和打包。
- 浅色、深色、两种圆角、四种强调色下都正常。
- 桌面和 375px 窄屏都不溢出。
- 沿用既有规则：浮层不自动弹出；投影只作层级信号（飘动的 emoji 是真正浮在内容上的元素，但它是瞬时装饰，不加投影）。

## 第二期：真实访客数据

### 托管

页面发布到 GitHub Pages。它只负责发页面；访客之间互通数据要靠一个外部的实时频道，由浏览器直接连接。

发布需要做的事：

- `vite.config.ts` 设置 `base` 为仓库路径（`/satin-ui/`）。
- 加一个 GitHub Actions 工作流，推送到 `main` 时打包并发布。
- 在仓库设置里开启 Pages。

### 实时频道

只用"在线成员"和"广播"两项功能，不用数据库。

| 候选 | 倾向 | 说明 |
| --- | --- | --- |
| Ably | 首选 | 只做频道和在场，闲置不暂停项目 |
| Supabase Realtime | 备选 | 免费项目闲置约一周会被暂停，不适合平时流量很小的展示页 |
| 浏览器点对点直连（如 Trystero） | 不采用 | 访客彼此能看到对方的 IP 地址，公开页面不应接受 |

各家的免费额度和条款是凭记忆写的，**动手前要查官方文档确认**，包括同时连接数上限和消息量上限。

### 各项数据怎么得到

| 数据 | 做法 |
| --- | --- |
| 在线人数 | 每个访客进入频道的"在线成员"，人数就是成员数；断线由服务自动移除 |
| 反应 | 点赞时向频道广播一条消息，所有在线访客收到后各自飘心 |
| 本场计数与峰值 | 每个访客在本地累计。新访客进入时向频道询问，已在线的访客回复自己手里的数字，新访客取其中最大值。所有人离开后自然归零 |
| 走势线 | 每个访客从自己进入时开始取样，不同步历史 |

访客没有账号。头像和名字由页面随机生成（颜色加字母），只在本次访问有效，不收集任何个人信息。

### 防刷

没有数据库不等于没人捣乱。计划的措施：

- 发送端限速：每人每秒最多若干次反应，超出的只在本地飘，不广播。
- 接收端限速：同一来源短时间内的消息超过阈值就忽略。
- 计数同步时丢弃明显异常的值（比如比当前在线人数能产生的上限高出几个数量级）。
- 密钥只开放这一个频道的订阅、发布和在场权限。

说明：密钥会公开在页面代码里，页面端的限制挡不住有心人。对展示页来说够用，最坏结果是数字被刷乱，所有人离开后会归零。如果以后要更严格，需要加一小段服务端代码来签发临时凭证，那就不再是纯静态了。

### 人少时的观感

展示页大部分时间可能只有一两个访客。

- 真实数字照实显示，不虚增。
- 没有真实反应时，飘心仍按演示节奏偶尔出现，但演示产生的反应**不计入**真实计数。
- 界面上用一个小标记区分状态：真实数据时显示"实时"，退回模拟时显示"演示"。

### 降级

- 连不上实时服务、被拦截、额度用完时，数据层状态变为 `offline`，自动退回第一期的模拟器，页面不报错。
- 恢复后自动切回真实数据。
- 没有配置密钥的构建（比如本地开发、别人克隆仓库）直接使用模拟器。

### 完成标准

- 两个浏览器窗口同时打开：在线人数为 2；一边点赞，另一边飘心且计数一致；关掉一个窗口后人数回到 1。
- 断网时退回模拟，恢复后切回真实。
- 快速连点不会让另一端卡顿或计数失控。

## 实现前需要知道的

- 第五屏第一期不依赖第三、四屏，可以先做，也可以按 3、4、5 的顺序做。
- 屏数增加后控件条的圆点会变多：五屏时窄屏底部条需要重新确认宽度。
- 包体积会继续涨，按屏拆分加载应在加到第三屏之前做。
- 第二期需要你本人注册实时服务的账号并创建项目，之后的配置和代码可以代写。
- 实时服务和 GitHub Pages 在中国大陆都不稳定。如果主要访客在大陆，第二期要换一套托管和实时服务方案。
